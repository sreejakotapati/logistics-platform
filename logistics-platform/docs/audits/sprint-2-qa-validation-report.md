assumed. The CI workflows were inspected as YAML (GitHub Actions cannot execute here); Docker images were
inspected (the Docker daemon is unavailable here, so image builds are validated by CI, not locally). Two

## Sprint 2 QA Report — per module

### 1. Database — **PASS**

**Findings.** Seven migrations form a clean linear chain (`0001_foundation` → `0007_rbac`); revisions and
`down_revision` pointers are consistent with no branches. UUIDv7 primary keys are generated by
`app.uuid_generate_v7()`. Every business table carries the standard audit columns
(`created_at/updated_at/created_by/updated_by`), soft delete (`deleted_at`), and optimistic-lock `version`;
`audit_logs` is deliberately append-only (no `updated_*`/`deleted_at`/`version`). Foreign keys are present
throughout with `ON DELETE CASCADE` on the join tables (`role_permissions`, `user_organization_roles`,
`auth_refresh_tokens`). Uniqueness is enforced with partial indexes filtered on `deleted_at IS NULL`
(emails, slugs, GSTIN, memberships, primary-membership, system/org role names), and read paths are indexed
(audit `(organization_id, created_at DESC)`, actor, entity, action). `updated_at` triggers are attached to
all seven mutable tables; `audit_logs` immutability is enforced by a `deny_mutation` trigger on
`UPDATE`/`DELETE`. RLS is applied via the reusable `app.enable_org_rls()` (which does `ENABLE` **and**
`FORCE` plus an `org_isolation` policy with both `USING` and `WITH CHECK`), with permissive read policies
for shared system rows (`organization_id IS NULL`). The RLS integration suite (34 tests) passes live and
confirms cross-tenant reads/writes are blocked, missing tenant context is **fail-closed** (NULL active org
→ zero rows), `app_superadmin` (BYPASSRLS) behaves as the approved bypass, and the table owner is still
constrained by `FORCE`.

**Risks.** None blocking. Migration `0003` redundantly re-runs `ENABLE/FORCE ROW LEVEL SECURITY` on
`roles`/`role_permissions` (idempotent, harmless).

**Missing tests.** None material — RLS coverage is strong.

**Missing documentation.** None; `database-architecture.md`, `secure-core-schema.md`,
`database-naming-conventions.md`, and `migrations.md` are present.

**Recommended fixes.** Remove the redundant RLS re-enable in `0003` (Low). Note: Alembic cannot run inside
this sandbox (a local psycopg/SQLAlchemy interaction); migrations were validated here with a direct SQL
applier and are validated by `alembic upgrade head` in CI — this is environmental, not a defect.

### 2. Authentication — **PASS**

**Findings.** Registration, login, refresh rotation, refresh-reuse detection (consumed/rotated token replay
→ whole family revoked), logout, password reset, and email verification all pass end to end. Access tokens
are short-lived JWTs carrying `sub`, `org`, `type`, `jti`, `iat`, `exp`; refresh tokens are stored only as
SHA-256 hashes. The refresh cookie is `httpOnly`, `SameSite=lax`, scoped to `/api/v1/auth`. Login timing is
equalised against a dummy hash to avoid user enumeration.

**Risks (resolved this pass).** The refresh cookie's `Secure` flag depended on an env var that was absent
from every example file and defaulted to `False` — a production deployment following the examples would
have shipped a non-Secure refresh cookie. **Fixed** (see Security Review H-1).

**Missing tests.** Auth service/router have no committed pytest coverage (24%/40%); flows are validated only
by external e2e scripts.

**Missing documentation.** None; `auth-service.md` is present.

**Recommended fixes.** Commit the auth e2e as repo tests (Sprint 3 entry criterion).

### 3. Tenancy — **PASS**

**Findings.** Active-organization context is carried in the JWT `org` claim and propagated to Postgres via
the `app.current_org_id` GUC on the RLS session. Organization switching validates membership and mints a
**new** JWT; the tenant session is created per request; membership is validated on switch. The tenancy
e2e (11/11) confirms isolation and that the active org survives refresh.

**Risks.** None.  **Missing tests.** Tenancy is covered by RLS integration + e2e.  **Missing docs.** None
(`multi-tenancy.md`, `tenancy-context.md`).  **Recommended fixes.** None.

### 4. RBAC — **PASS**

**Findings.** Authorization is exclusively permission-based (`require_permission`,
`require_platform_permission`); a code search found **no** role-name authorization checks. Multiple role
assignments, custom org roles, and platform-admin permissions resolve correctly. The Redis permission cache
is keyed per `(user, scope)`, is best-effort (fail-open to DB), and is invalidated on every role
assign/remove and on platform-admin changes (`invalidate_user`). Every assignment is audited. RBAC e2e
(20/20) passes.

**Risks.** None.  **Missing tests.** RBAC service at 28% committed coverage.  **Missing docs.** None
(`rbac-authorization.md`).  **Recommended fixes.** Commit RBAC e2e (Sprint 3).

### 5. Audit — **PASS**

**Findings.** Audit events are created across modules; immutability is enforced at the database (trigger)
and verified by integration test; CSV/JSON export, keyset-paginated timeline, and the actor/entity views
work; tenant feeds are org-scoped while platform/security events (org NULL) are visible only through the
platform feed. Audit e2e (21/21) passes including tenant-vs-platform isolation.

**Risks.** None.  **Missing tests.** Audit service at 36% committed coverage.  **Missing docs.** None
(`audit-logging.md`).  **Recommended fixes.** Commit audit e2e (Sprint 3).

### 6. Security — **PASS**

**Findings.** Password policy, rate limiting (429 with `Retry-After`/`RateLimit-*`), account lockout
(returns the **same generic 401** as a wrong password — no enumeration), session listing/revocation,
hardening headers (CSP correctly skipped on `/docs`), CSRF origin verification on cookie-bearing unsafe
requests, abuse monitoring, and platform-scope security-event auditing all pass (34 + 5 checks). Redis
outage was simulated live: register/login still succeed (controls fail-open) while a wrong password still
returns 401 — confirming **no weakening** of the underlying password control.

**Risks (resolved this pass).** `jwt_secret` defaulted to `change_me` with no fail-fast guard. **Fixed**
(see Security Review H-2).

**Missing tests.** Security service at 44% committed coverage; controls validated by external e2e only.

**Missing documentation.** None; `security-hardening.md` and `redis-strategy.md` are present.

**Recommended fixes.** Commit security e2e and add a CI step that runs it against service containers.

### 7. API — **PASS**

**Findings.** OpenAPI generates cleanly (47 paths). The error envelope `{code, message, details,
request_id}` is consistent across `AppError`, request-validation (422 `validation_error`), HTTP, and
unhandled paths. Pagination is keyset-based (audit). Dependency injection is via FastAPI `Depends`;
exception handlers are registered centrally. Standard response schemas live in `app/shared`.

**Risks.** None.  **Missing tests.** No contract/snapshot test pins the OpenAPI schema.  **Missing docs.**
`docs/api/` is a placeholder.  **Recommended fixes.** Add an OpenAPI snapshot test (Low).

### 8. Infrastructure — **PASS WITH WARNINGS**

**Findings.** `docker-compose.yml` runs postgres/redis/backend/frontend with healthchecks and
`depends_on: service_healthy`; the backend image is multi-stage and runs as a non-root `appuser`; liveness
(`/health`, dependency-free) and readiness (`/ready`, returns 503 when DB/Redis down) are separated.
Secrets are externalised (the `secrets/` directory is empty bar a README; the production example uses
`__from_secret_manager__`).

**Warnings.** `docker-compose.yml` ships `change_me_*` default passwords for local convenience (acceptable
for local, must never reach staging/prod — the staging compose and env examples should be the only path).
Stale `S1-T5/S1-T6 scaffold` comments remain in the Dockerfile and compose. The production cookie/secret
configuration gap (now fixed in code) originated here.

**Missing tests.** No automated smoke test asserts `/ready` returns 503 on dependency loss (verified

`staging-deployment.md` present).  **Recommended fixes.** Remove stale comments; add a readiness smoke test.

### 9. CI/CD — **PASS WITH WARNINGS**

**Findings.** Six workflows exist and are coherent: backend-ci (ruff, mypy, `alembic upgrade head`, unit
coverage, **required** RLS integration job with `RLS_ADMIN_DSN`), frontend-ci (lint, type-check, build,

**Missing tests.** Flow-level e2e absent from CI (the central testing gap).  **Missing docs.** None

## Security Review

### Critical risks
None.

### High risks

**H-1 — Refresh cookie not marked `Secure` in production (FIXED).** `cookie_secure` defaulted to `False`
and was absent from every env example; the code read the setting directly with no production override. A
production deploy following the examples would have transmitted the httpOnly refresh token without the
`Secure` flag. **Fix applied:** a settings validator now forces `cookie_secure=True` whenever
`APP_ENV ∈ {staging, production}`, and `COOKIE_SECURE=true` was added to the staging/production env
examples. Verified: prod settings report `cookie_secure=True` even when the env tries to disable it; local
unaffected.

**H-2 — Weak default `JWT_SECRET` with no fail-fast (FIXED).** `jwt_secret` defaulted to `change_me`; a
production deploy that forgot to set it would issue forgeable tokens. **Fix applied:** the same validator
rejects boot in staging/production if `JWT_SECRET` is empty, equal to `change_me`, or shorter than 32
characters. Verified: production boot with `change_me` now raises; local/CI (APP_ENV=local) unaffected and
the full suite still passes (36 pytest + all e2e).

### Medium risks

**M-1 — CI security/quality gates not enforcing.** Coverage gate, Trivy gating, and dependency-audit
gating are all still report-only despite being scheduled for Sprint 2. CI will not fail on regressions in
those dimensions. *Not fixed* (CI policy change, non-blocking to functionality; recommended for immediate
Sprint 3 action).

**M-2 — Service-layer test coverage 55%, flow tests outside the repo.** auth/rbac/organizations/audit/
security service layers are 24–44% covered by committed tests; their flows are validated only by e2e
scripts that are not in the repository or CI. Functionality is proven today but unprotected against
regression. *Not fixed* (requires committing a test suite — Sprint 3 entry criterion).

**M-3 — Dependencies floor-pinned, no hash-locked manifest (backend).** `requirements.txt` uses `>=`
ranges; reproducibility relies on resolution time. Dependabot is configured. *Not fixed* (recommend a
pinned/compiled lockfile).

### Low risks
Redundant RLS re-enable in migration `0003`; stale scaffold comments in Docker/compose; local-only default
passwords in `docker-compose.yml`; frontend has no unit tests (lint/type/build only); no OpenAPI snapshot
test.

## Technical Debt Report

The debt is concentrated in test automation and CI enforcement rather than in the product code, which is
consistent and well-structured. The highest-leverage item is **committing the HTTP-flow e2e suites into the
repository and wiring them into CI**: they already exist and pass, so this is packaging work, not new test
design, and it would lift effective coverage of the service layers from the low-20s/40s into a meaningful
range and close the regression gap. Second is **turning on the three deferred CI gates** (coverage,
container/filesystem vulnerability scanning, dependency auditing), which the codebase was explicitly written
to adopt in Sprint 2. Third is **dependency pinning** for reproducible builds. Minor debt: redundant DDL in
`0003`, stale scaffold comments, two un-regenerated tracker spreadsheets, and an empty `docs/api/`. None of
these are functional defects; all are quality-of-life and safety-net improvements.

## Sprint 2 Exit Review

### Decision: **Sprint 2 — CONDITIONALLY APPROVED**

All nine feature tasks are implemented and **independently verified to function** against live PostgreSQL +
Redis (128 e2e checks plus 36 committed pytest tests, all green). The two High-severity production-security
defects discovered during this QA pass were **fixed and re-verified** within scope (config hardening only —
no new features, modules, or architectural change). The conditions below are Medium-severity and concern the
regression safety net and CI enforcement rather than delivered functionality; they do not warrant rejection,
but they must be closed early in Sprint 3 before the codebase grows further.

**Conditions to clear (carry into Sprint 3, close before S3 feature work):**
1. Commit the auth/tenancy/organizations/RBAC/audit/security e2e suites into `backend/tests` and add a CI
   job that runs them against Postgres + Redis service containers.
2. Enable the three deferred CI gates: `--cov-fail-under` (start at a realistic floor and ratchet up),
   Trivy `exit-code: 1` for CRITICAL/HIGH, and remove `continue-on-error` from the dependency audits.
3. Regenerate the two pending tracker spreadsheets referenced in the sprint/audit docs.

### Sprint 3 Entry Criteria
- The three conditions above are closed (flow tests in CI; gates enforcing; trackers regenerated).
- `main` is green on all six workflows with the new gates active.
- Backend coverage gate active and passing at the agreed floor.
- No open Critical/High defects (currently none — H-1 and H-2 fixed).

### Outstanding Risks
- Regression exposure until the flow tests are in CI (M-2) — highest residual risk.
- CI will not block new vulnerabilities/coverage drops until the gates are enabled (M-1).
- Reproducibility depends on dependency resolution time until a lockfile is committed (M-3).
- No load/performance or external security testing has been performed yet (expected, pre-Sprint-3).

### Recommended Next Steps
1. Land the committed e2e suites + CI flow job (1–2 days; tests already exist).
2. Flip the three CI gates and fix anything they surface.
3. Pin backend dependencies; regenerate the trackers; clean up stale comments and the `0003` redundancy.
4. Schedule a short performance/load baseline and an external security review during Sprint 3 hardening.

**Sprint 2 may be marked complete once the three conditions are cleared.** The delivered functionality is
sound and verified; the gating items are about protecting it going forward.
